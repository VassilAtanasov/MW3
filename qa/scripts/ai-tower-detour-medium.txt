#   dotnet run --project src/MW3.Desktop -- --map medium --time-scale 20
#     --script qa/scripts/ai-tower-detour-medium.txt --dump-state dump.txt
#
# WHAT THIS BUILDS. On Medium the human upgrades its start base to level 2, takes the neutral at
# (0.35, 0.25) - base 2, the slot nearest the obstacle's lower-left routing corner - upgrades it,
# feeds it from base 3, and CONVERTS IT TO A TOWER through the real action menu. That tower sits
# 0.058 from the inset corner (0.40, 0.28), well inside its level-1 range of 0.20, so it covers the
# corner every southern detour around the obstacle turns on. The human then empties base 0, and the
# AI attacks it. Two derived expectations follow, both checkable in the dump.
#
# DERIVED EXPECTATION 1 - the AI prices its send along the polyline, not the line.
# The dumped Army line reads Source=5 Target=0, and Arrival - Launch = 2061 - 2000 = 61 ticks.
# Base 5 is (0.65, 0.75) and base 0 is (0.12, 0.50). Their straight-line separation is
# sqrt(0.53^2 + 0.25^2) = 0.586003, which at ArmySpeedUnitsPerTick = 0.01 would be ceil(58.60) = 59
# ticks. The route is blocked by the obstacle (x 0.42..0.58, y 0.30..0.70), so PathCalculator turns
# it at the inset corner (0.40, 0.72): 0.251794 + 0.356090 = 0.607884, which is ceil(60.79) = 61.
# 61, not 59, is what the dump must read. That is derived from the two coordinates and the tuning
# constants, not read off this build, and it fails if the AI reverts to straight-line arithmetic.
#
# DERIVED EXPECTATION 2 - the tower's threat, hand-computed both ways.
# The pair this tower actually taxes is the AI's own start base 1 (0.88, 0.50) attacking base 0
# (0.12, 0.50). A level-1 tower has RangeUnits = 0.20 and FirePeriodTicks = 6, so at speed 0.01 an
# army covers 0.06 units between shots and the estimate is floor(chord / 0.06).
#   STRAIGHT LINE: y = 0.50 from x 0.88 to x 0.12 runs a constant 0.25 from the tower at
#   (0.35, 0.25) - outside 0.20 - so the chord is 0 and the OLD two-point estimate is 0. Costing
#   nothing, straight-line scoring predicts base 0 as the cheapest target from base 1.
#   POLYLINE: the line is blocked, so the route is (0.88, 0.50) - (0.60, 0.28) - (0.40, 0.28) -
#   (0.12, 0.50), length 0.356090 + 0.20 + 0.356090 = 0.912180. Segment 1 never comes closer than
#   0.251794. Segment 2 enters range at t = 0.261314 and runs to its end: 0.738686 x 0.20 = 0.147737.
#   Segment 3 starts inside range and leaves at t = 0.598776: 0.598776 x 0.356090 = 0.213208.
#   Summed = 0.360945, and floor(0.360945 / 0.06) = floor(6.0157) = 6. The NEW estimate is 6, so
#   polyline scoring prices that same attack at six units lost and prefers any untaxed target.
#   Note what the sum does: flooring PER SEGMENT would give floor(0.147737/0.06) = 2 plus
#   floor(0.213208/0.06) = 3, i.e. 5 - one unit short. 6 is only reachable by summing the chords
#   first and flooring once, which is the rule this feature pins.
#
# WHAT THIS SCRIPT DOES NOT PROVE, stated rather than left to be assumed. Expectation 2's target
# preference is not observable here: making the AI CHOOSE differently needs it to hold a full-cap
# forward base while at least two non-AI bases besides the tower are winnable, and the human cannot
# reach that board unattended - a conversion costs 30 units, which the human's single start base
# cannot fund until roughly tick 1400, by which time the AI owns every neutral and clause 4 has one
# target left to order. The preference flip is therefore pinned headlessly, in
# AiRouteAwareThreatTests.TryAttack_OnAnObstacleLayout_OrdersTargetsByRouteLengthNotStraightLine and
# EstimateUnitsLost_ATowerOnTheDetourButNotOnTheStraightLine_GoesFromZeroToSix - the same division
# ai-contests-forge.txt already draws: real play proves the reachable end-to-end path, headless
# tests prove the arithmetic real play cannot cheaply exercise.
#
